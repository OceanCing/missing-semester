## 5.虚拟内存/虚拟存储器（Virtual Memory)

- 虚拟内存=内存（主存RAM）+硬盘（辅存SSD/HDD）

  > ps:
  >
  > ①内存很贵，很快，容量小（eg16G），硬盘很便宜，慢，容量大（eg1TB），1TB=1024GB
  >
  > ②NUC(Next Unit of Computing)，是迷你电脑主机，含有CPU，内存，硬盘，风扇，通常有2个内存插槽（16G）
  >
  > ③换页（paging）：内存不够用时，用硬盘当备用装数据
  >
  > ④映射：操作系统当“前台“，用对照表把”虚拟地址“翻译成”物理地址“

- 它让每个程序（进程）都以为自己独占整个电脑的内存
- 作用：①将主存看成一个存储在磁盘（硬盘）上的地址空间的高速缓存，在主存中只保存活动区域（正在用的），并根据需要在磁盘和主存之间来回传送数据，高效利用主存

> ps:
>
> ①高速缓存好比喻啊，但是其实从交换空间（Swap Space)的定义上看（硬盘上专门划出来的一块区域，用来当内存的“备胎”），相对于CPU缓存，内存又是下一级存储，不是缓存。
>
> 即：CPU寄存器<-L1/L2/L3缓存<-内存<-磁盘
>
> ②页面调度：操作系统（OS=Operating System)把内存和硬盘切成一个个固定大小的”页“，通常是4KB,这样内存满了后，将内存中暂时不用的”页“从硬盘拉进内存
>
> ③中央处理器CPU：工厂（里面刻着好几套独立的运算电路，即核Core）
>
> ​    核CoreL:工人（脑）
>
> ​    进程Process：工人正执行的大工程  eg:视觉程序，底盘控制程序
>
> ​    线程Thread：工程里的具体小任务（一进程一般会多线程）

​                  ②统一进程地址（以虚拟地址编址），从而简化了存储器管理，方便写代码

​                  ③隔离程序

- 区分

  | **主存储器（物理实体）-----即主板上的内存条RAM**             | **内存空间（逻辑概念）----页面调度下，每个”页“有一个地址，这些”页“的集合叫内存空间** |
  | ------------------------------------------------------------ | ------------------------------------------------------------ |
  | **虚拟存储空间（物理实体的假想版）----内存条+硬盘的交换空间** | **虚拟地址空间（逻辑概念的假想版）-----见下图**              |

- 虚拟地址空间
![image](images/image-20261025220346757.png)

1. 地下0层（只读的代码和数据）：房子建好时的硬装。放着你的程序本体（.0文件链接后的东西），也包括了 1ibc.so 里的不可修改数据。只能看，不能砸
2. 地上1层（读/写数据）：你买的家具（全局变量）。随时可以修改
3. 地上2层（运行时堆 Heap）：空仓库。你的程序喊一句 malloc（或者C++的new），仓库就往上盖一层（图中的向上箭头）。用完得自己拆（free/delete），不拆就内存泄漏
4. 中间的空气（蓝色空隙）：未分配的空地。如果指针瞎指到这里，MMU 没给你分配物理
5. 内存，直接报 Segmentation fault（段错误）
6. 地上3层（共享库映射区）：这和图右边画了printf 函数。当你的程序跑起来，系统发现你要用 printf，就把硬盘里的 libc.so这个“集装箱”直接映射到了这一层。所有程序都在这一层共享 1ibc.so，节约内存。
7.  地上4层（用户栈 Stack）：你平时吃饭的餐桌。你调用一个函数，就摆一个盘子；函数跑完，盘子收走。它和“堆”的生长方向是反的，它是从下往上长，往下的箭头表示空间在扩展。

> ps: 
>
> ①“堆（Heap）”是你向系统申请来的“大仓库”，用来存大型数据。(箭头朝上)
> 而“栈（Stack）”，是程序运行时的“临时工作台”，它只用来存“临时变量”和“函数调用”（箭头朝下）
>
> ②内存泄漏（Memory Leak）：用 new 或 malloc 在堆 （Heap）上租了内存，但是程序跑完后，忘了写delete或free 把它还回去，最后这块内存就被永久锁死了，程序如果反复跑，租的仓库越来越多，电脑内存被吃光，整个系统卡死崩溃。（本质：这是只有手动管理内存的语言，如C/C++才会得的“绝症”，但像 Python或Java有“自动垃圾回收GC，会自动帮你退租，不会这样）

## 6.静态链接器（static linker)

- 其以一组**可重定位目标文件**和**命令行参数**作为输入，生成一个完全链接的，可以加载和运行的**可执行目标文件**为输出

> ps:①可重定位目标文件：由各种不同的代码和数据节组成（selection节，每一节都是一个连续的字节序列）
>
> ②可执行即完全独立！

- 下图是一个运行在Linux的x86-64系统，使用标准的ELF-64可重定位目标文件格式：

 ![image](images/image-20261025222311625.png)

（以下是完全粘贴的链接内容，因为已经写的很清晰了）

1. ELF头（ELF header）：以一个16字节的序列开始，这个序列描述了生成该文件的系统的字的大小和字节顺序。ELF头剩下的部分包含帮助链接器语法分析和解释目标文件的信息。其中包括ELF头的大小、目标文件的类型（如可重定位、可执行或者共享的）、机器类型（如x86-64）、节头部表（section header table）的文件偏移、以及节头部表中条目大小和数量。不同节的位置和大小是由节头部表描述的，其中目标文件中每个节都有一个固定大小的条目（entry）。
2. 夹在ELF头和节头部表之间的都是节

| **.text**     | **已编译程序的机器代码**                                     |
| ------------- | ------------------------------------------------------------ |
| **.rodata**   | **只读数据，比如printf语句中的格式串和开关语句的跳转表**     |
| **.data**     | **已初始化的的全局和静态C变量。局部C变量在运行时被保存在栈中，即不出现在.data节中，又不出现在.bss节中** |
| **.bss**      | **未初始化的全局和静态C变量，以及所有被初始化为0的全局或静态变量。在目标文件中这个节不占据实际的空间，它仅仅是一个占位符。目标文件格式区分已初始化和未初始化变量是为了空间效率：在目标文件中，未初始化变量不需要占据任何实际的磁盘空间。运行时，在内存中分配这些变量，初始值为0** |
| **.symtab**   | **一个符号表，它存放着在程序中定义和引用的函数和全局变量的信息** |
| **.rel.text** | **一个.text节中位置的列表，当链接器把这个目标文件和其他文件组合时，需要修改这些位置。一般而言，任何调用外部函数或者引用全局变量的指令都需要修改。另一方面，调用本地函数的指令则不需要修改** |
| **.rel.data** | **被模块引用或定义的所有全局变量的重定位信息。一般而言，任何已初始化的全局变量，如果它的初始值是一个全局变量地址或者外部定义函数的地址，都需要被修改** |
| **.debug**    | **一个调试符号表，其条目是程序定义的局部变量和类型定义，程序中定义和引用全局变量，以及原始的C源文件** |
| **.line**     | **原始C源程序中的行号和.text节中的机器指令之间的映射**       |
| **.strtab**   | **一个字符串表，其内容包括.symtab和.debug节中的符号表，以及节头部中的节名字。字符串表就是以null结尾的字符串序列** |

> > ps:
> >
> > 占位符：
> >
> > 1.用处：
> >
> > ①因为不知道printf这个函数代码最终会被放到内存里哪个地址，所以放个占位符，最后再链接器“填坑”（对应.rel.text节）
> >
> > ②让没有初始值的全局变量不占硬盘空间（对应.bss节）
> >
> > 2.大小：占位符通常是4个字节（32位）或8个字节（64位），其大小完全取决于你电脑CPU的”寻址能力“，若电脑的CPU是64位的（即CPU一次可以处理64个0和1），其录址时用的就是一个64位的二进制数
>
> *---->联系上面说的：若在代码里写了printf,编译器在.rel.text(重定位节)里留下的占位符，其实就是一个8字节的坑，在真实生成的.o文件里，这个坑里可能填的全是00 00 00 00 00 00 00 00（或者全是FF），这时链接器就会把真实的0X4005A0这个地址，转换成8个字节的二进制序列（比如00 00 00 00 00 00 40 05 A0）*

- 静态链接过程

1. 核心概念：ELF 可执行文件结构

![image](images/image-20261025230150541.png)

如图所示，经过链接后，多个目标文件被合并为一个可执行目标文件。它的内部被划分为不同的节（Section），并在加载时按属性分组：

| **只读内存段（代码段）**  | **.init, .text (机器码), .rodata (只读数据)。加载后只可读/执行**** |
| ------------------------- | ------------------------------------------------------------ |
| **读/写内存段（数据段）** | **.data (已初始化全局/静态变量), .bss (未初始化全局/静态变量)。加载后可读/写**** |
| **不加载到内存**          | **.symtab (符号表), .debug (调试信息), .line, .strtab。这些仅供链接和调试使用，不占用运行时内存** |

2.静态链接的三大步骤

①空间和地址分配

| **动作**     | **扫描所有输入的目标文件，获取各段的长度、属性；收集所有符号定义和引用，放入全局符号表** |
| ------------ | ------------------------------------------------------------ |
| **合并**     | **将所有输入文件的同类段合并（例如把 A 的 .data 和 B 的 .data 拼在一起）** |
| **分配**     | **计算合并后各段的位置，并建立与虚拟地址空间的映射**         |
| **关键细节** | **在链接前，各个独立目标文件的虚拟地址都是 0（未分配）；链接完成后，可执行文件中的各段就会被分配到统一的虚拟地址** |

②符号解析 (Symbol Resolution)

目标：将代码中的每个“符号引用”与其唯一的“符号定义”关联起来。找不到定义就会报错（undefined reference）

符号表区分：

| **全局符号**           | **可被其他模块引用**                 |
| ---------------------- | ------------------------------------ |
| **外部符号**           | **在其他模块定义，当前模块引用**     |
| **局部符号（static）** | **仅在当前模块可见，不可被外部引用** |

> ps：.symtab 不记录局部非静态变量（它们运行时在栈上管理），但 static 局部变量有记录

多重定义处理（Linux 规则）：

  · 函数和已初始化全局变量 = 强符号 (Strong)
  · 未初始化全局变量 = 弱符号 (Weak)
  · 规则：① 不允许多个同名强符号；② 强符号与多个弱符号同名，选强符号；③ 多个同名弱符号，任选其一。

③重定位 (Relocation)

合并完段并解析完符号后，链接器开始把“占位符”替换为真实地址。

| 重定位节和符号定义   | 合并同类型节，将运行时内存地址赋给新的聚合节、及内部每条指令和全局变量。此时，所有指令和变量都有了唯一地址 |
| -------------------- | ------------------------------------------------------------ |
| 重定位节中的符号引用 | 依赖可重定位模块中的“重定位条目”，修改代码/数据中的引用，让它们指向正确的运行地址（即填平之前留下的坑） |

3. 程序加载 (Loading)

静态链接完成后，程序还在硬盘上。当你敲下 ./prog 时：

①Shell 识别到这是可执行文件，调用操作系统的加载器 (Loader)（Linux 下通过 execve 函数）

②加载：加载器将可执行文件中的代码和数据，从磁盘复制到内存中

③执行：跳转到程序的入口点（第一条指令），程序正式化身进程开始运行



- 动态链接与共享库（Dynamic Linking）

1. 为什么需要动态链接？（解决静态链接的痛点）

①更新噩梦：静态库一旦更新，所有使用它的程序都必须手动重新编译、重新链接
②空间浪费：如果 10 个程序都用同一个静态库，磁盘里会有 10 份副本；同时运行它们，内存里也会有 10 份副本

2. 核心概念：共享库（.so）

①共享方式：全系统只有一个 libxxx.so 文件。所有程序只保留引用，不复制代码
②内存极致利用：运行时，同一份 .text（代码段）可以被多个不同进程共享读取

3. 动态链接的构建流程（命令行）

   ①造库（生成共享目标文件）

   ```
   gcc -shared -fpic -o libvector.so addvec.c multvec.c
   ```

> ps:
>
> -shared：告诉链接器，我要生成的是共享库（.so）
> -fpic：生成位置无关代码（Position-Independent Code），方便在内存任意位置加载

​     ②链接程序

```
gcc -o prog21 main2.c ./libvector.so
```

> ps:此时生成的 prog21 是“部分链接”的可执行文件。它内部没有复制 libvector.so 的代码，只复制了“重定位和符号表信息”（相当于留了填空题和目录）
>

4.程序的加载与执行

![image](images/image-20261025235104551.png)

当你敲下 ./prog21 时，背后的魔法是这样发生的：

①加载器接手：操作系统的加载器（Loader）把 prog21 搬进内存

②发现线索：加载器发现 prog21 里有个 .interp 节，里面写着：“我不是完整的，你需要去找动态链接器”

③召唤外援：加载器不直接运行程序，而是先启动动态链接器（ld-linux.so）

④动态重定位（填坑）：动态链接器把 libc.so 和 libvector.so 的代码映射到内存，然后修改 prog21 里的引用（把前面的填空题填上真实地址）

⑤交接控制权：一切就绪，动态链接器把 CPU 控制权交给 prog21 的入口点，程序正式运行

> ps：一旦连好，共享库在内存中的位置就固定了，直到程序结束
>

5. 进阶：从应用程序中动态加载

| 场景 | 高性能服务器（eg： Web 服务器）                              |
| ---- | ------------------------------------------------------------ |
| 做法 | 不必每次收到请求都 fork 一个新进程。服务器可以在运行期间，动态地加载某个共享库中的函数并调用 |
| 好处 | 函数会一直缓存在内存中，后续请求只需极小的函数调用开销，性能直接拉满 |



# 二，CMake

-  CMake 


1.本质：跨平台的构建系统生成工具
2.作用：你不必再手写冗长的 g++ 命令。只需编写 CMakeLists.txt 配置文件，CMake 会自动生成对应平台的构建文件（如 Linux 下的 Makefile）
3.核心语法：命令名(参数列表)

- 核心指令速查表（按项目构建逻辑排序）


1. 基础声明

①版本限定：cmake_minimum_required(VERSION 3.10)（必须放在最顶部）
②项目定义：project(MyProject VERSION 1.0.0 LANGUAGES CXX)（CXX 代表 C++）

2. 构建目标（产出物）

①生成可执行文件：add_executable(MyApp main.cpp utils.cpp)
②生成库文件：add_library(MyLib STATIC library.cpp)

| STATIC----静态库（.a / .lib） | SHARED----动态库（.so / .dll） |
| ----------------------------- | ------------------------------ |
| 编译时直接嵌进程序            | 运行时加载                     |

3. 依赖与链接（现代 CMake 核心）

①添加头文件路径：

```
target_include_directories(MyApp PRIVATE ${PROJECT_SOURCE_DIR}/include)
```

| PRIVATE      | PUBLIC                                 | INTERFACE                                |
| ------------ | -------------------------------------- | ---------------------------------------- |
| 只有自己能看 | 自己能看，依赖我的人也能看（公开 API） | 自己不看，只给依赖我的人看（纯头文件库） |

②链接库：

```
target_link_libraries(MyApp PRIVATE MyLib)
```

4. 进阶设置

①设置变量：

```
set(CMAKE_CXX_STANDARD 17)
```

 或 

```
set(SOURCES main.cpp utils.cpp)
```

②安装规则：（执行 make install 时文件去哪）

```
install(TARGETS MyApp RUNTIME DESTINATION bin)
```

③条件语句：（常用于 Debug/Release 模式切换）

```
if(CMAKE_BUILD_TYPE STREQUAL "Debug") ... endif()
```

④ 自定义命令：

```
add_custom_command(TARGET MyApp POST_BUILD COMMAND echo "构建完成!"
```

-  普通变量 vs 缓存变量

| **特性**     | **普通变量**            | **缓存变量 (Cache)**                                       |
| ------------ | ----------------------- | ---------------------------------------------------------- |
| **定义语法** | **set(MY_VAR "value")** | **set(MY_VAR "value" CACHE PATH "描述")**                  |
| **作用域**   | **当前及子目录**        | **全局生效**                                               |
| **生命周期** | **每次运行重新计算**    | **存入 CMakeCache.txt，持久化保留**                        |
| **修改方式** | **直接改代码**          | **命令行输入 -D 覆盖（如 cmake .. -DENABLE_LOGGING=OFF）** |

> ps:修改了代码里缓存变量的默认值，需删除 CMakeCache.txt 或整个 build 目录才会生效
>

-  查找第三方库 (find_package)


① 基本用法：find_package(Boost 1.70 REQUIRED)（找不到直接报错中止）
②现代推荐做法：使用导入目标，而不是手动拼接路径变量

```
find_package(Boost REQUIRED)
target_link_libraries(MyApp PRIVATE Boost::Boost) # 自动处理头文件和库文件路径
```

- 标准工作流（外部构建）


永远不要在主目录直接 cmake，这会产生一堆垃圾文件。请执行外部构建：

```
$ mkdir build && cd build     # 建隔离的构建目录
$ cmake ..                    # 读取上一级的 CMakeLists.txt，生成 Makefile
$ cmake --build .             # 开始编译（其实就是调用了 make）
$ cmake --install .           #（可选）安装到系统目录
```

> ps:
>
> 1. 彻底抛弃全局指令：不要用 include_directories() 和 link_directories()，它们会造成路径污染。只用 target_xxx 系列
> 2. 必须指定 C++ 标准：写上 
>
>    ```
>    set(CMAKE_CXX_STANDARD 17) 和 set(CMAKE_CXX_STANDARD_REQUIRED ON)
>    ```
>
>    防止编译器用老古董标准
> 3. 吃透可见性关键字：自己用 PRIVATE，给外部用 PUBLIC
> 4. 找第三方库不手拼路径：一律用 find_package + 导入目标。

一、 核心心智模型 (Mental Model)

AI 编程助手的本质，是一个拥有工具箱的大模型在和你对话。

1. 用户输入需求（如“建个文件”）
2. LLM（大模型）思考后，决定调用工具，并输出结构化指令（JSON）
3. 你的程序在本地执行该工具（LLM 本身不碰文件系统）
4. 执行结果返回给 LLM
5. LLM 基于结果继续对话或执行下一步。（这就是完整的 Agent Loop）



二、 三大核心工具 (The Three Tools)

一个能写代码的 Agent，起步只需要三个基础工具：

1. read_file (读文件)：获取文件完整内容。返回包含路径和内容的字典（为了给 LLM 提供结构化上下文）

2. list_files (列目录)：遍历文件夹，返回文件名和类型（文件/目录）

3. edit_file (改文件)：最复杂的工具，处理两种情况：
   · 如果 old_str 为空：创建/覆盖文件
   · 如果 old_str 不为空：在文件中找到它，并替换为 new_str

   

三、 核心架构代码拆解

1. 脚手架 (Scaffolding)

·resolve_abs_path：路径解析工具，确保输入 file.py 能转换为绝对路径 /Users/you/project/file.py
· TOOL_REGISTRY (工具注册表)：一个字典，将工具名称映射到对应的 Python 函数，方便 LLM 根据名字查找并执行

2. 系统提示词 (System Prompt) —— 最关键的一步

通过提示词告诉 LLM：

· 你的角色（编程助手）
· 你能用的工具列表及说明（通过解析函数的 docstring 和签名自动生成）
· 强制调用的格式：tool: TOOL_NAME({"arg": "value"})（必须是一行紧凑的 JSON）

3. 解析器 (Parsing Tool Calls)

· extract_tool_invocations：解析 LLM 的文本回复。逐行扫描，一旦发现以 tool: 开头的行，就提取函数名和 JSON 参数，准备在本地执行

4. 核心引擎：Agent 循环 (The Agent Loop)

这是整个系统的灵魂：

· 外层循环：获取用户输入 -> 追加到对话历史
· 内层循环：
  · 调用 LLM
  · 解析是否有工具调用
  · 如果无工具调用：直接打印回复，跳出内层循环，等待用户下一次输入
  · 如果有工具调用：在本地执行工具 -> 将结果以 tool_result({...}) 格式追加到对话历史 -> 继续循环（这允许 LLM 连续执行多个动作，比如先读文件，再改文件，最后确认）



四、 生产级工具 (Claude Code)

| 特性     | 生产级工具 (如 Claude Code)             |
| -------- | --------------------------------------- |
| 错误处理 | 复杂的容错、回退机制                    |

# 四，ROS 1 (Catkin) 工作空间

> ！ 核心认知：
>
> ①CMake 是单项目包工头（管一个程序）
> ②Catkin 是 ROS 1 的超级包工头（基于 CMake，统筹整个工作空间内的几十个互相依赖的功能包）

-  Catkin 标准工作流


第一步：创建工作空间 (Creating a workspace)

动作：建立一个大厂房（Workspace），并在里面划出 src（源码）区域。
命令：

```
mkdir -p ~/catkin_ws/src
cd ~/catkin_ws/src
catkin_init_workspace
```

> 底层逻辑：告诉系统“我以后所有写机器人的代码，都放在这个大文件夹里”

第二步：创建功能包 (Creating a ROS Package)

动作：在 src 里隔出独立的小车间（Package）。比如“视觉包”、“底盘控制包”。
命令：

  ```bash
  catkin_create_pkg my_package std_msgs roscpp
  ```
> ps：std_msgs 和 roscpp 是该包依赖的其他包，系统会自动写入其 package.xml 和 CMakeLists.txt 中(底层逻辑：实现代码模块化，互不干扰)

第三步：一键编译 (Building packages)

动作：回到工作空间根目录，执行终极咒语。
命令：

```
cd ~/catkin_ws
catkin_make
```

> 底层逻辑：Catkin 自动扫描 src 下的所有包，并调用底层 CMake，按依赖关系把所有代码编译成可执行文件，放入 devel 目录

第四步：工作空间叠加 (Overlaying)

> 动作：在不同层级建多个工作空间，实现“私房小灶”。
> 底层逻辑：系统运行程序时，优先在最顶层的空间找，找不到再去底层的空间找。适合在不破坏基础环境的前提下测试新代码

-  注意：


①历史遗留：图左侧的 rosbuild 是极其古老的构建工具，直接无视（无需学习）。

②ROS 1 停更：图顶部的蓝色横幅提示，ROS 1 (Noetic) 将于 2025 年 5 月停止支持 (EOL)。但这不影响你们打机甲大师（RM），目前主流仍是 ROS 1，基础逻辑与 ROS 2 相似。

source devel/setup.bash
```

(否则系统会找不到你刚编译出来的程序)
