##make

  *make是一个命令工具，是一个解释Makefile中指令的命令工具，而make工具在构造项目的时候需要写一个叫做Makefile的文件，make作为批处理命令，去逐条执行Makefile里面的命令，makefile关系到整个工程的编译规则，可以说学习Makefile就是学习make中的核心内容。*

  *在了解Makefile之前，我们有必要去先了解一下Makefile在干什么？Makefile实际上就是一个脚本文件，里面告诉编译器怎么去编译相应的源文件，而编译源文件的整个过程为：**源代码->预处理->编译->汇编->链接->可执行程序**。(Cmake是另一种项目构建方式，但是跟Makefile比更高级，能够根据不同的平台自动生成相应的Makefile，一般来说在项目只有一两个源文件的时候可以直接编辑Makefile,但当项目文件变多时，或者需要跨平台管理时，使用Cmake是更好的选择。)*
- **关于Makefile**：
1. 规则：Makefile的框架是由规则构成的，而规则的基本格式为:
```make
#每条规则的语法格式;
target1,target2...:depend1,depend2,...
	command
	......
	......
```
2. 在调用 make 命令编译程序的时候，make 会首先找到 Makefile 文件中的第 1 个规则，分析并执行相关的动作，若其他规则是用来生成第一项规则里面的依赖的，那么这些规则也将会被执行，需要注意的是Makefile中第一条规则及其所有依赖的相关规则被执行后make的任务就完成了，剩余没有被涉及到的规则，倘若想要执行它，那在make的时候在make后面添加其对应的target。
3. make命令执行的时候会根据文件的时间戳判断是否执行makefile文件中相关规则中的命令；并且make有自动推导能力。[^1]
4. *Makefile里面可以使用变量：自定义变量，预定义变量和自动变量。*
- 自定义变量：在创建一个变量名的同时要给其赋值，在使用变量时，只需要`$(变量名)`就可以取出变量值了。
- 预定义变量：在Makefile中有一些已经定义好了的变量，用户可以直接使用这些变量，不用进行定义。[^1]
- 自动变量：自动变量用来代表规则中经常会出现的目标文件和依赖文件，并且它们只能在规则的命令中使用。[^1]
5. 模式匹配：%是一个通配符，%.o:%.c代表了所有.o为结尾的目标文件和.c为结尾的依赖文件将按照以下写的规则进行，避免了相似规则的重复和繁琐。
6. 函数：makefile中有很多函数并且所有的函数都是有返回值的。其格式为`$(函数名 参数1, 参数2, 参数3, ...)`。常用函数如下：
- wildcard:这个函数的主要作用是获取指定目录下指定类型的文件名，其返回值是以空格分割的、指定目录下的所有符合条件的文件名列表。
- patsubst:这个函数的功能是按照指定的模式替换指定的文件名的后缀,例：`$(patsubst <pattern>,<replacement>,<text>)`。

##Cmake

  *Cmake一个跨平台的构建系统生成工具，用于管理C/C++项目的编译过程，根据写好的CMakeLists.txt，可以去定义项目的构建规则、依赖关系和编译选项，Cmake会自动生成对应平台的构建系统。*
1. 执行Cmake过程会生成一些目录和文件，这个时候可以单独建一个目录build，将这些与项目源码无关的文件统一放到一个对应的目录里边。
2. cmake后会得到一个Makefile.txt文件，然后make,就可以得到相应的可执行文件或者库文件等了。
3. CMakeLists.txt里面基础格式例如：
```cmake
cmake_minimum_required(VERSION 3.0.0)
project(CALC)
add_executable(app add.c div.c main.c mult.c sub.c)
```
4. 常用：
- 设置变量：`set()`
- 搜索文件： `aux_source_directory()`查某个路径下的所有源文件 / file()可以选择搜索当前目录或者是递归搜索当前目录的相应文件类型 
- 包含头文件：`include_directories(headpath)`
5. 库：
- 添加库：`add_library(库名称 STATIC 源文件1 [源文件2] ...)` STATIC可以换成SHARED,就代表生成动态库
- 指定输出的路径：用`set()`来指定输出路径,`EXECUTABLE_OUTPUT_PATH`指的是可执行文件输出路径，而动态库是具有可执行权限的，可以用它来设置动态库的生成路径,`LIBRARY_OUTPUT_PATH`同上，但既适用于动态库又适用于静态库。
- 链接库文件：
```cmake
target_link_libraries(
	<target>
	<PRIVATE|PUBLIC|INTERFACE> <item>... 
	[<PRIVATE|PUBLIC|INTERFACE> <item>...]...)

)
```
- 指出自己创作的库的位置：`link_directories(path)`
6. 日志：message()显示一条用户消息[^2]
7. list命令的多种用法包括但不限于`APPEND`追加/`REMOVE_ITEM`字符串移除等。[^2]
8. 宏定义：在进行程序测试的时候，我们可以在代码中添加一些宏定义，通过这些宏来控制这些代码是否生效，例如：
```cmake
#ifdef DEBUG
    printf("我是一个程序猿, 我不会爬树...\n");
#endif
```
*如果DEBUG被定义，则printf命令生效，若没有被定义，则相当于printf被注释掉*  
9. 预定义宏[^2]   
10. 嵌套的CMake:在一些大型项目里面，通过给每个源码目录添加一个CMakeLists.txt文件，让这个项目更灵活更便于管理和维护。
- 节点关系：众所周知，Linux的目录是树状结构，所以嵌套的 CMake 也是一个树状结构，最顶层的 CMakeLists.txt 是根节点，其次都是子节点。需要注意的是：关于CMakeLists.txt根节点中的变量全局有效；父节点中的变量可以在子节点中使用；子节点中的变量只能在当前节点中使用。
- 添加子目录:`add_subdirectory(source_dir [binary_dir] [EXCLUDE_FROM_ALL])`通过这种方式CMakeLists.txt文件之间的父子关系就被构建出来了。
- 根节点的CMakeLists.txt文件主要做了两件事情：定义全局变量和添加子目录。子目录下则主要干构建库和所需要的可执行文件，可以说，子目录的CMakeLists.txt把项目的各个部分分成小的模块，而根节点的CMakeLists.txt统筹了整体的子目录的CMakeLists.txt,让子目录有序进行，各司其职。

##Catkin

  *Catkin 是 ROS 基于 CMake 封装出来的构建系统，底层依旧依赖 CMake，目的是标准化 ROS 功能包的结构、依赖管理、编译、环境配置。gcc/g++ <- make <- cmake <- catkin其实就是一层一层更高的抽象：从一开始gcc/g++这种比较底层更加贴近机器的编译器，到make通过Makefile自动化调用gcc/g++等编译器，cmake去自适应平台构建makefile让make更容易，而catkin再在cmake的基础上做一层封装，专门适配ROS,标准化ROS功能包的结构、依赖管理、编译、环境配置，让大型项目的cmake更容易。它们最终的目标都一致：借助工具链把源代码转换为可执行程序。*     
- Catkin工作区的src目录下的功能包：里面常见有(不限于)src,build，include，devel目录，src里面存放的是源文件代码，build是cmake时的目录，有makefile和中间文件的产生，而include则是存放头文件的目录，devel是开发空间，放置开发过程中的可执行文件和库,这些目录名字都不能乱改的，并且这些目录里面的文件也不能随意放置到别的目录里面去，这是标准化ROS功能包的结构、依赖管理、编译、环境配置的重要基础。除此之外，里面还有自动生成的CMakeLists.txt和package.xml,里面分别存放的是功能包的编译规则；功能包的描述信息，这两者都是必须要存在在功能包里面的。
- Catkin工作区:创建了新的工作区要用`catkin_init_workspace`初始化工作空间，创建src目录，在此src目录里面放置功能包。

##程序详细编译过程

以下是关于考核链接1的相关笔记：    
**要在系统上运行由CPP编写的程序，就必须把这些.cpp/.c转化为可执行目标文件，过程分为四个阶段：预处理(%.i)、编译(%.s)、汇编(%.o)、链接,执行这四个阶段的程序：预处理器、编译器、汇编器、和连接器**。  
1. 程序编译的整体流程：     
- 预处理(-E)：在这个阶段主要做了三件事: 展开头文件 、宏替换 、去掉注释行。     
- 编译(-S): 这个阶段需要GCC调用编译器对文件进行编译, 最终得到一个汇编文件。     
  编译过程可分为6步：**扫描（词法分析）、语法分析、语义分析、源代码优化、代码生成、目标代码优化。**     
- 汇编(-c): 这个阶段需要GCC调用汇编器对文件进行汇编, 最终得到一个二进制文件。      
- 链接: 各种代码和数据片段收集并组合成为一个单一文件的过程，这个阶段需要GCC调用链接器对程序需要调用的库进行链接, 最终得到一个可执行的二进制文件。    
2. 虚拟内存    
- 虚拟内存又叫虚拟存储器（Virtual Memory），是建立在主存--辅存物理结构基础上，有附加的硬件装置及操作系统存储管理软件组成的一种存储体系。是一个抽象概念，它为每个进程提供了一个假象，即每个进程都在独占地使用主存。每个进程看到的内存都是一致的，称为虚拟地址空间。    
- 三大核心作用：高速缓存，高效利用物理主存；统一地址空间，简化内存管理；内存隔离，提供保护。   
3. 静态链接     
   
4. 动态链接共享库    

5. 从应用程序中加载和链接共享库:动态加载共享库：将生成动态内容的函数封装进共享库；Web请求到来时服务器动态加载并直接调用该函数，替代 fork+execve；函数缓存在服务地址空间，后续请求开销小。

##cmake 基础
  
以下是关于考核链接2的笔记(若上面已出现过的内容则将不再重复):   
1. 除了`include_directories(headpath)`还可以用`target_include_directories(<target> [PUBLIC | PRIVATE | INTERFACE] <headpath>)`。  
  **一般使用target_include_directories()**，因为相比另一个，在使用时它更具备优势：  
- 仅作用于指定的目标，不污染其他目标；  
- 推荐优先使用，符合现代 CMake 最佳实践；  
- 显式绑定到指定目标，依赖关系一目了然；  
- 较好，路径与目标绑定，逻辑清晰；  
- 通过 PUBLIC、PRIVATE、INTERFACE 精确控制。  
2. **PUBLIC**：当前目标和依赖它的目标都能使用该路径；  
  **PRIVATE**：只有当前目标能使用；  
  **INTERFACE**：只有依赖当前目标的其他目标能使用。  
3. 设置安装规则：  
```cmake          
install(TARGETS <目标>...
	[RUNTIME DESTINATION <可执行文件安装路径>]
        [LIBRARY DESTINATION <动态库安装路径>]
        [ARCHIVE DESTINATION <静态库安装路径>]
        [INCLUDES DESTINATION <头文件安装路径>])
# 定义执行 make install 时各类型文件的安装位置
```
4. 条件语句：`if(<条件>) ... elseif(<条件>) ... else() ... endif()`(CMake 支持的条件表达式包括：比较、逻辑运算、变量判断等)   
5. 自定义命令：  
```cmake
add_custom_command(
	TARGET <目标>
        PRE_BUILD | PRE_LINK | POST_BUILD
        COMMAND <命令> [参数...]
        [COMMENT <说明>]
        [VERBATIM])
# PRE_BUILD：在编译前执行
# PRE_LINK：在链接前执行
# POST_BUILD：在构建完成后执行
```
6. 缓存变量：缓存变量存储在 CMakeCache.txt 文件中，在多次 CMake 运行之间保持值不变。缓存变量通常用于让用户在 CMake 配置阶段自定义构建设置，例如开关功能或指定安装路径。例：  
```cmake
# 语法：set(<变量名> <默认值> CACHE <类型> <描述>)
# 类型可选：STRING、BOOL、PATH、FILEPATH
# 如果 CMakeCache.txt 中已有该变量，set 不会覆盖已有值

# 定义一个字符串类型的缓存变量（用户可修改的安装路径）
set(MY_INSTALL_PATH "/usr/local" CACHE PATH "程序的安装路径")

# 定义一个布尔类型的缓存变量（功能开关）
set(ENABLE_LOGGING ON CACHE BOOL "是否启用日志功能")

# 使用缓存变量和其他变量一样
if(ENABLE_LOGGING)
    message(STATUS "日志功能已启用")
    add_definitions(-DENABLE_LOGGING)
endif()
```
7. 查找库和包：`find_package()`会搜索系统中已安装的库，并设置对应的变量。

##The Emperor Has No Clothes: How to Code Claude Code in 200 Lines of Code

以下是关于考核链接3的相关笔记：  
- AI编码助理实际上的核心：  
1. 用户给出任务；  
2. LLM 输出结构化的工具调用指令；  
3. 本地程序执行文件操作工具；  
4. 将工具执行结果传回大模型；  
5. 模型基于返回信息继续规划，循环直到任务完成。  
  这就是整个循环，LLM实际上从未真正触及文件系统，只是通过工具跟本地文件互动，通过得知结果而利用这种上下文继续或做出回应。   
- 我们编码代理基本上只需要三项功能：读取文件；列出文件；编辑文件。  
1. 读取文件：取一个文件名，返回其内容(LLM需要通过读取文件知道关于发生事情的结构化背景)；   
2. 列表文件：通过列出目录内容来导航(以便导航项目)；   
3. 编辑文件：当查找的内容为空时创建新文件or通过查找并替换文本
- LLM需要知道有哪些工具并且如何调用它们，则此时需要`TOOL_REGISTRY={}`还有函数签名和文档字符串动态生成，而LLM会自行决定如何使用他们的。  
- 当LLM响应时，我们需要检测它是否在要求我们运行某个工具，找行的开头，提取函数名和JSON参数，来解析LLM的返回文本。  
- 上面说的AI编码助理的核心循环，负责来回收发 LLM 请求、执行工具、拼接消息历史。
- 而我们创作的大约只有200行简单的python的工具跟Claude Code这些正式产品的核心agent工具循环是一样的，只是正式产品比我们构建的多了更好的错误处理和后备行为；流式回复以提升用户体验等等，但核心循环同上，都是上述所说的循环和工具。
