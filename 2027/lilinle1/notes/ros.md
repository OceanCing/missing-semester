## 1. 核心架构认知与心智模型

### 1.1 ROS 的定位
- ROS 并非真正的操作系统，而是运行在 Linux 之上的**机器人中间件与通用工具箱**。
- 它提供了统一的底层硬件抽象、进程间消息通信（IPC）、代码管理以及完善的可视化调试生态（rviz、rqt、rosbag）。

### 1.2 战队方案：纯上位机架构
- **算控一体**：将目标检测、坐标解算、PID 闭环控制和决策状态机全部放在上位机（NUC/MiniPC）的 ROS 节点中运行。
- **传输与控制解耦**：上位机通过 EtherCAT 周期帧直接输出电机的力矩与位置指令；下位机只负责总线帧转换（EtherCAT ⇄ CAN）与安全急停兜底，没有控制逻辑。
- **优势**：改算法、调参数只需在上位机终端敲 `catkin build` 重新编译即可，告别繁琐的单片机硬件烧录固件与双端通信协议对齐。

### 1.3 ROS Master 的真相
- **Master 仅负责“登记与牵线”**：Master（端口 11311）只在节点启动时记录发布者和订阅者的名字、类型、IP 与端口。
- **数据点对点直传**：配对成功后，节点之间建立的是底层 TCP 直连，**数据流完全不经过 Master**。Master 挂掉后，已经连上的数据通信依然能正常运行。

## 2. 节点间的核心通信机制

ROS 提供三种基础通信方式，分别应对不同的场景需求：-

| 通信方式                       | 机制与模型                | 典型场景                           | 关键机制与注意事项                                                         |
| :------------------------- | :------------------- | :----------------------------- | :---------------------------------------------------------------- |
| **话题 (Topic)**             | 异步广播、发布/订阅、多对多       | 相机图像、雷达点云、底盘速度指令 /cmd_vel      | 发送方不关心接收方是谁；接收回调函数跑在 `ros::spin()` 线程中，**严禁写耗时阻塞操作**，否则会导致队列溢出丢包。 |
| **服务 (Service)**  | 同步阻塞、请求/应答、一对一       | 模式切换、清屏 `/clear`、生成乌龟 `/spawn` | 必须等待服务端返回结果；未上线时直接调用会卡死，必须配合 `waitForExistence()` 和客户端超时检测。       |
| **参数服务器 (Param)** | 共享配置表、Key-Value 树状字典 | 相机曝光增益、限位阈值、PID 增益             | 数据寄生在 Master 内存中；适合启动时读取，不适合高频传输连续变化的数据流。                         |
|                            |                      |                                |                                                                   |

## 3. 工作空间与功能包规范

### 3.1 工作空间（catkin_ws）目录分工
- `src/`：功能包源码目录（唯一需要进 Git 版本管理的地方）。
- `build/`：编译中间缓存文件，可随时清理。
- `devel/`：编译产出目录，包含可执行文件与最核心的环境变量激活脚本 `setup.bash`。
- **环境变量机制**：新开终端必须 `source devel/setup.bash`，终端才能通过 `ROS_PACKAGE_PATH` 找到自己编写的功能包。

### 3.2 功能包（Package）核心两件套
1. **`package.xml`**：
   - 包名必须与文件夹名严格一致。
   - 依赖声明区分编译依赖（`<build_depend>`）与运行依赖（`<exec_depend>`），或直接使用 `<depend>`。
2. **`CMakeLists.txt`**：
   - `find_package(catkin REQUIRED COMPONENTS ...)` 引入依赖库。
   - 自定义消息三件套：`add_message_files()`、`add_service_files()`、`generate_messages()`。
   - **排错避坑**：可执行目标务必添加依赖保护 `add_dependencies(target ${${PROJECT_NAME}_EXPORTED_TARGETS})`，防止编译顺序错乱导致“找不到自定义消息 `.h` 头文件”。

## 4. 配置文件（YAML）与参数管理

### 4.1 YAML 的核心语法规则
YAML 是通过“缩进”来定义层级关系的通用配置格式，必须遵守五条硬规则：
1. **严格禁止使用 Tab 键**，统一使用 2 个空格缩进。
2. **冒号后面必须紧跟一个空格**（正确：`key: value`；错误：`key:value`）。
3. **大小写敏感**，布尔值在 ROS 中严格为 `true` / `false`。
4. **注释使用 `#`**。
5. 核心结构由**标量**（数字/字符串）、**列表**（`- item`）和**字典**（键值对）嵌套组成。

### 4.2 ROS 中的配置加载与读取
- **规范的参数文件示例 (`config/params.yaml`)**：
```yaml
camera:
  exposure: 30
  gain: 1.2
pid:
  kp: 1.5
  ki: 0.0
  kd: 0.1
```
## 常用ROS命令
### 1. 节点与运行管理（`rosnode`） 
```shell
rosnode #列出当前正在运行的所有节点名
rosnode info <节点名> #打印该节点发布了哪些话题、订阅了哪些话题,提供了哪些服务以及网络 IP 端口
rosnode ping #测试与该节点的通信延迟
rosnode kill #关闭节点
```
### 2. 话题通信诊断（`rostopic ` & rqt_graph`）
```shell
rostopic list #列出系统当前所有活跃的话题
rostopic echo #实时打印话题传过来的数据
rostopic info #查看该话题的消息类型,以及谁在发、谁在收
rqt_graph #直观画出当前所有节点和话题的拓扑连线
```
### 3. 服务与调用（rosservice`）(不太懂)
```shell
rosservice list #列出当前可用的所有服务
rosservice type #查看该服务使用的是哪种 .srv 格式
rosservice call <服务名> <参数> #在终端手动填入参数并触发一次服务调用

```
### 4. 参数服务器配置（rosparam`）
```shell
rosparam set <参数名> <数值> #在程序运行中动态修改参数
rosparam get <参数名> #验证刚才改的参数生效没有
rosparam load <yaml文件> [命名空间] #把YAML文件里的参数一次性灌入系统
rosparam dump <yaml文件> [命名空间] #把内存里的参数倒回成YAML文件保存到硬盘上
rosparam list #当节点报“找不到某个参数”或者读出来的是默认值时，敲 `rosparam list | grep xxx` 看一眼这个参数到底有没有成功注册到内存里、名字有没有写错层级
```
